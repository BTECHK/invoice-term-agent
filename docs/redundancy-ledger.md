# Native capabilities and redundancy ledger

The sandbox replay demonstrates proposal and exception controls with local fixtures. This ledger separates what SAP already does natively, what a BI or process-analytics platform may offer, what the agent adds, what is only a local stand-in in this repository, and which controls stay. It proposes no control removal or production integration. All model-facing write tools stay denied, and payment release remains a human responsibility under this project's policy.

## Where the agent adds value

Value levers: working capital (pay on the longest valid term instead of early), early-payment discounts taken only when they beat the cost of capital, fewer manual term checks in accounts payable (AP), no payment on a term nobody agreed, and evidence plus an audit trail for every decision. SAP holds the data and runs the match, the payment block and the payment run. The table shows, area by area, where SAP already covers the ground and what the agent adds on top.

## Responsibility and retention

| Area | Native capability and source | Agent value | Local stand-in in this repository | Retained control, and removal candidate only after replacement evidence |
|---|---|---|---|---|
| Read the printed term | SAP Document AI supports invoice schemas and extraction; capture is not a novel capability [S1]. Which capture product the organization licenses is open (Q-7). | Preserve the exact printed text, page, quote and uncertainty, so the printed term can be set against the purchase order (PO) and vendor terms. This is the input that exposes a term nobody agreed. | Curated extraction fixtures; live reading remains Design. | Source grounding and unreadable-field routing stay. Removal candidate: a separate capture layer, if the licensed capture product delivers equivalent cited fields and error handling. |
| Compare three terms | SAP holds the term on the PO and in the vendor master, and invoice entry (MIRO) carries a term onto the posted document. Which term SAP proposes at entry, and whether anyone compares it with the printed term, depend on customer configuration and process. Both are unverified here, so no source is cited. | Compare the printed invoice term with the PO and vendor terms and find the longest valid term, so payment is not made early and not made on a term nobody agreed. The printed term is an additional source, not proof of the SAP posted term. | None. The comparison runs in code (`rules.py`, `propose.py`) on rows read through the ERP data service, which `mock_erp/` stands in for locally. | Printed-term reconciliation, provenance and validated-term approval rules stay. Removal candidate: repeated SAP-side mismatch calculation, once the native coverage is verified. |
| Match, receipt and block | SAP invoice verification owns receipt, quantity and price variance checks and payment blocking [S2]. | Read match, approval and receipt state as evidence and send the exception to a person with that evidence attached, so the clerk does not rebuild the case by hand. | None. SAP's state is copied and never recomputed. | The agent cannot clear a SAP block or perform a replacement three-way match. Conservative routing on missing or stale state stays. Removal candidate: local imitation of native block determination, after the data contract supplies authoritative current state. |
| `total_variance_pct` versus OMR6 | SAP OMR6 has company-code tolerance keys for distinct price, quantity, date and amount checks [S2]. | An early, conservative flag that sends a value mismatch to a person before any payment day is proposed. | The 1% total-variance screen and line thresholds are pilot policy checks, not OMR6 parity. They neither reproduce all tolerance keys nor change SAP's posting or block result. | The current fail-closed control stays until replaced. Removal candidate: duplicate screening, only after a signed mapping to the customer's tolerance settings and tests of partial receipts, currency and invoice lines. |
| Terms over 60 days | German Civil Code (BGB) section 271a(1) has conditions for agreements over 60 days, including express agreement and absence of gross unfairness; public-authority rules differ [S3]. | Deterministic routing of every term over 60 days to a person for confirmation, so a long term is never applied without a recorded agreement. A validated term alone is not legal approval, and this check is not a full legal determination. | None. The routing is code. | The escalation and the approved evidence of applicable agreement stay. Removal candidate: none on current evidence. Any native replacement must preserve both. |
| Discount versus capital | SAP payment configuration already uses discount limits and tolerance days [S4]. | Compare the annualized return of an early-payment discount with the approved cost of capital (5% assumed, Q-1), so a discount is taken only when it beats that cost and payment otherwise waits for the longest valid term. SAP owns due dates, payment selection and actual discount capture. | The 5% rate is an assumption held in `policy/term-rules.yaml`, not read from a finance system. | Deterministic arithmetic and independent checking stay. Removal candidate: duplicate calculation, if an approved native implementation provides the same comparison and evidence. |
| Independent recheck | Native term and tolerance checks, where present, do not establish an independent check of this proposal [S2]. | A separate deterministic context re-queries trusted inputs and recomputes. Disagreement removes the actionable day and sends both values to a person, so a wrong proposal does not reach a payment day. | The deterministic checker in the sandbox. Different-family live model checking remains Design. | The recheck stays. Removal candidate: none. Native overlap is not evidence that proposal rechecking is redundant. |
| Exception worklist | A failed tolerance check in invoice verification sets a payment block that a person releases after review [S2]. How blocked items are assigned, tracked and reported depends on the customer's process and is unverified here. | The evidence pack and recommendation for each exception: the three terms, the query result behind each figure, the money impact and a drafted recommendation. The agent does not invent an AP worklist. | Files in `worklist/` expose review evidence. Landing in an existing worklist remains Design. | Exception records and human review stay. Removal candidate: local worklist files, after the target worklist's assignment, evidence, status and access behavior are proven. |
| Audit, locks, journal and idempotency | SAP change documents record business changes [S5]. | One hashed event per tool call, allowed or denied, tied to the invoice. A controller can check a decision long after the run, including proposals that were rejected or never applied. | Files and process coordination protect this sandbox workflow. SAP change records alone do not establish exactly-once cross-system execution or capture rejected proposals. | Correlation, proposal evidence and replay protection stay. Removal candidate: local storage and locking mechanics, after durable production storage, concurrency, deduplication and recovery meet the same obligations. |
| Duplicate detection | SAP invoice verification can check for a duplicate invoice at entry when the check is active for the vendor. Its criteria and activation are customer configuration and are unverified here. | Delivery protection: invoice-ID and digest replay suppression, and conflict detection when a changed invoice arrives under a used ID. This is distinct from business-duplicate detection. | Local invoice-ID and semantic-hash checks in `cli.py` and `worklist.py`. | Do not remove transport idempotency. Removal candidate: any future locally invented fuzzy business-duplicate detector, when native coverage is verified. |
| Approval | SAP authorization roles control who may release a payment block or change a document; their design at the deploying organization is unverified here. Change documents record the change [S5], and posted-document change rules limit which fields can change [S6]. A separate approval workflow with forms is the proposed interface for the agent's proposals; it is not an SAP feature, and its behavior is unverified here. | The form shows the three terms, the evidence and the proposed term or baseline date, so approval is an informed decision and not a bare yes. The agent never approves. | Local approval records. Authenticated approval remains Design; a form response does not grant SAP authorization or prove segregation of duties. | The approval gate stays. Removal candidate: local approval-record plumbing, only after authenticated identity, delegation, expiry and evidence are proven. |
| SAP write | An approved ERP action through SAP's standard change interface (a BAPI or an RFC-enabled function module) is the candidate path. Exact modules and required setup are unverified here. Posted-document change rules and allowed fields require customer testing [S6]. | The agent proposes the exact term or baseline date with its evidence and never writes. A person's approval turns the proposal into one deterministic action with approved values only. | None. Design only; no enabled write exists. | Denied model write tools, approval and readback stay. Removal candidate: none. Reuse a validated native path rather than introduce an agent SAP client. |
| Payment run | SAP selects items using payment parameters, discounts, tolerance days and blocks, then posts payments and clears items [S7]. | None inside the run. A proposal changes what the run selects only after a person approves a term or baseline date change. This is not a claim that SAP lacks scheduling. | None. No local payment engine exists. | The human release boundary stays: the agent neither schedules nor releases payment, and an authorized person releases each run under project policy. Removal candidate: none. |
| A BI or process-analytics platform | A BI or process-analytics platform may offer its own term comparison, duplicate detection, worklists, forms, workflow history or outcome tracking. These differ by product and version and are unverified here; none is cited or assumed. | Stages ingestion-ready records and the evidence behind each proposal, so any such platform reads the same structured data. The agent adds the printed term and a hashed decision trail. | Local files in `worklist/` and `audit/` and the schemas in `schemas/`. No platform integration is built. | All current controls stay. Removal candidate: a local stand-in, only after the platform's equivalent is verified in the target environment and its owner, equivalence evidence and failure behavior are recorded. |

## Evidence status and sources

Reviewed 2026-10-29. Verified means official page content or official indexed text was readable, not that the capability is installed or configured at the deploying organization. SAP learning pages labelled S/4HANA describe native concepts; they do not prove identical ECC customer configuration. The ledger describes them as one generic class without a source, and each one needs verification in the target environment before anything depends on it.
